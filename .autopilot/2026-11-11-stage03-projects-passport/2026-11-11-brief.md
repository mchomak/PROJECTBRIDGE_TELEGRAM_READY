**# Stage 03 — Projects and Project Passport**

**Goal:** Allow an authenticated executor to create and manage a project
and its initial passport.

Stage 02.

## Scope

### Backend

- Implement Project, ProjectMember, and ProjectPassport models and
  migrations.
- Support the four initial project types only: `website`,
  `telegram_bot`, `automation`, `other`.
- Enforce one active executor and one active customer per project.
- Create Project, executor membership, and passport atomically.
- Implement project list, create, detail, update, member list, complete,
  and archive operations described in the API contract.
- Implement passport read and executor update.
- Add passport `version` handling and return `409 Conflict` for stale
  updates.
- Ensure all project reads and writes are scoped to active project
  membership and role.

### Frontend

- Project list page.
- Project creation flow with the four project types.
- Project overview page.
- Passport view/edit experience for executor.
- Read-only passport view for customer once a customer membership
  exists.
- Loading, empty, validation, and error states.

## Out of scope

- Customer invitation flow.
- Questionnaire and passport auto-population.
- Project State entities.
- Progress percentages.
- Public freelance-order import.

## Deliverables

- Project and membership models.
- ProjectPassport model and service layer.
- Project and passport API endpoints.
- Project list/create/detail UI.
- Permission and concurrency tests.

## Acceptance criteria

- [ ] A verified authenticated user can create a project.
- [ ] Project, executor membership, and passport are created in one
  transaction.
- [ ] Only the four agreed project types are accepted.
- [ ] A user sees only projects where they are an active member.
- [ ] Only the executor can update project metadata and passport
  directly.
- [ ] Both project participants can read the passport.
- [ ] A stale passport update returns `409 Conflict` and does not
  overwrite newer data.
- [ ] Duplicate active executor/customer memberships are prevented.
- [ ] Tests cover cross-project access and role violations.

## Stop conditions

The exact passport field set must follow `DATA_MODEL.md` and the
questionnaire mapping decisions. If the current product document defines
different required fields, surface the discrepancy instead of silently
adding/removing fields.

## Codex handoff

Implement Stage 03 only. Build the project and passport vertical slice,
including UI, API, migrations, permissions, and tests.

## Дополнения

### 2026-11-11

Спасибо, корректно остановился. Фиксируем правила жизненного цикла проекта для MVP.

**1. Статусы проекта**

Используем четыре статуса:

- `draft` — исполнитель создал проект, заполняет паспорт и готовит его к работе.
- `active` — полноценная работа над проектом.
- `completed` — проект завершён, доступен только для чтения.
- `archived` — проект перенесён в архив, доступен только для чтения.

**2. Переходы между статусами**

- `draft → active` — после принятия приглашения заказчиком.
- `active → completed` — исполнитель завершает проект.
- `completed → active` — исполнитель может повторно открыть проект.
- `draft / active / completed → archived` — исполнитель может архивировать проект.
- `archived → previous_status` — исполнитель может восстановить проект в том статусе, в котором он находился до архивирования.

Для восстановления необходимо сохранять предыдущий статус. Можно добавить поле `status_before_archive` в модель Project. После восстановления оно очищается.

Изменять статус проекта может только исполнитель.

**3. Доступ после завершения проекта**

В статусе `completed`:

- Оба участника сохраняют доступ ко всем данным проекта на чтение.
- Паспорт проекта доступен только для чтения.
- История чата доступна для просмотра, отправка новых сообщений запрещена.
- Документы можно просматривать и скачивать, загружать новые нельзя.
- Project State доступен на чтение, изменения запрещены.
- Новые ответы на анкету не принимаются.
- Исполнитель может повторно открыть или архивировать проект.

**4. Доступ после архивирования**

В статусе `archived`:

- Проект скрывается из основного списка и отображается в отдельном разделе архивных проектов.
- Оба участника сохраняют доступ ко всем существующим данным на чтение.
- Все операции изменения данных заблокированы.
- Исполнитель может восстановить проект. При восстановлении он возвращается в предыдущий статус.

Архивирование не означает удаление проекта или его документов.

**5. Паспорт проекта**

Подтверждаю использование предложенного набора полей из `DATA_MODEL.md`.

Для Stage 03:

- Используем описанную там структуру паспорта.
- Не добавляем самостоятельно новые бизнес-поля.
- Не определяем дополнительные обязательные поля.
- Логику обязательности ответов и сопоставления ответов анкеты с полями паспорта оставляем за Stage 05.

Заказчик не редактирует паспорт напрямую. Его ответы на анкету будут обрабатываться по отдельным правилам на следующем этапе.

**6. Хранение данных**

Пока не реализуем автоматическое удаление завершённых или архивных проектов. Сроки хранения 12 месяцев и 14 дней не считаем утверждёнными продуктовыми требованиями.
