# T08 - Deliver chat events over authenticated WebSockets

## What must work

A committed message reaches the other active project participant over a project-specific authenticated WebSocket. Reconnect reloads REST history and duplicate events do not add duplicate rows.

Message submission remains REST-only. The WebSocket consumer delivers
committed `message.created` events and does not accept client message
commands. The existing per-user rate limit applies to new REST
submissions; replayed IDs do not consume the limit.

## From the brief, verbatim

> Reconnecting clients can recover messages missed while disconnected.

## Spec sections

Spec sections 4.4, 5, and 6. Update the API/architecture contract for session-authenticated, project-scoped chat delivery; REST remains authoritative.

## Acceptance criteria

- [ ] WebSocket connection requires an authenticated active project member and joins only the matching project group.
- [ ] Events are emitted after the database commit, delivered only to that project, and deduplicated in the client by message ID.
- [ ] Reconnect restores missed messages from REST history; network/rate-limit errors are recoverable and do not lose the compose text.
- [ ] Tests cover unauthenticated/nonmember rejection, cross-project isolation, publication timing, reconnect recovery, and the existing REST rate-limit/429 retry path; the WebSocket has no client send operation.
