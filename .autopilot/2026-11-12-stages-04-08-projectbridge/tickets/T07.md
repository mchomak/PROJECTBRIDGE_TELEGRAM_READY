# T07 - Persist chat messages and provide REST history and sending

**Requirements:** R45, R59, R60, R61, R64, R68, R69, R100i, R101i, R102i
**Blocked by:** T06
**Zone:** backend/apps/chat/; backend/apps/project_state/; frontend/src/entities/chat/; frontend/src/features/chat/; frontend/src/pages/projects/
**Wave:** 7
**Status:** done

## What must work

Both participants read cursor-paginated PostgreSQL history and send text through an idempotent REST endpoint. The chat UI preserves failed drafts for retry; Project State can validate a same-project message as Evidence.

## From the brief, verbatim

> REST persistence is authoritative; WebSocket is only a live-delivery channel.

## Spec sections

Spec sections 3, 4.3, 4.4, 5, and 6. Add the chat source selector to Project State without direct cross-app writes.

## Acceptance criteria

- [ ] REST history uses stable cursor pagination (default 50, maximum 100); send persists a bounded text message only for active projects.
- [ ] A repeated client message ID with identical content returns the prior message; reuse with different content returns 409 and never creates a duplicate.
- [ ] Both participants can read history in allowed statuses; project membership, per-user rate limit, 10,000-character limit, and audit-safe metadata are enforced.
- [ ] UI renders chronological history, loading/empty/error states, and sending/sent/failed messages; retry preserves the original client ID and content.
- [ ] The Project State Evidence selector accepts only an existing same-project Message and rejects unknown/cross-project message IDs; tests cover DB isolation and idempotency.
