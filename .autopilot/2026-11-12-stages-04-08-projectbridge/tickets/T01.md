## What must work

An executor can invite a normalized email address, see invitation status, and revoke a pending invitation. Delivery uses the configured local console email backend. The stored token is hashed; throttles and project status rules are enforced by services.

## From the brief, verbatim

> Only an executor can create or revoke invitations for their project.

## Spec sections

Spec sections 3, 4.1, 5, and 6. Update the invitation data model, API/security contract, OPEN_DECISIONS, and an ADR for expiry and rate-limit defaults.

## Acceptance criteria

- [ ] Executor-only create/list/revoke paths enforce normalized email, allowed project statuses, the active-customer uniqueness rule, 7-day expiry, and Redis-backed limits.
- [ ] Raw tokens are returned only in the outbound invitation link and never stored or logged; email delivery is observable through the console backend.
- [ ] The authenticated project UI creates invitations and shows pending, expired, accepted, and revoked states with recoverable validation and server errors.
- [ ] Tests cover permissions, normalization, status restrictions, expiry, revocation, throttling, and safe audit metadata.
